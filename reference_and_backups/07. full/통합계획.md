# GMP 컴퓨터화 시스템 통합 구축 계획

> 작성일: 2026-06-04 | 대상: 6개 GMP 실습 시스템(COA, LM, ELB, RIM, SEM, CVM)
> 목적: 6개 독립 시스템을 "하나의 통합 시스템(Suite)"으로 묶어, 단일 계정·중앙 계정관리·중앙 환경설정·통합 감사추적을 제공하고, 최종적으로 Vercel 배포 + 공유 DB로 발전시킨다.

---

## 1. 목표

1. **단일 로그인(SSO)** — 한 번 로그인하면 6개 시스템을 재로그인 없이 사용 (현재 1차 구현됨)
2. **중앙 계정관리** — 계정 생성·권한·활성화를 통합 포털 한 곳에서만 수행. 각 시스템 내부 계정관리 제거
3. **중앙 환경설정** — 회사명·자동 로그아웃 등 공통 설정을 포털에서 관리, 전 시스템에 전파
4. **통합 감사추적(선택)** — 전 시스템 감사 이력을 포털에서 한눈에 조회
5. **일관된 UX** — 동일 디자인 시스템, 동일 헤더, 시스템 간 자연스러운 이동
6. **배포 가능** — 교육 후 Vercel에 올려 수강생이 계속 접속 (장기: 공유 DB)

## 3. 통합 원칙 — 무엇을 공유하고 무엇을 분리하나

| 계층 | 통합(공유) | 개별(시스템 고유) |
|---|---|---|
| 인증/세션 | ✅ 통합 (SSO) | — |
| 계정·권한 | ✅ 통합 (`gxpsuite:users`) | — |
| 공통 환경설정 (회사명, 자동 로그아웃) | ✅ 통합 (`gxpsuite:settings`) | — |
| 감사추적 | ◐ 통합 뷰(조회) + 시스템별 기록 | 시스템별 원천 기록 유지 |
| 업무 데이터 (기록, 평가, 수불 등) | — | ✅ 시스템별 독립 |
| 시스템 고유 설정 (평가기준, 허용기준, 패스워드 정책 등) | — | ✅ 시스템별 |
| 업무 화면·워크플로우 | — | ✅ 시스템별 |

> 핵심: **"누가 쓰는가(계정)·어떻게 들어오는가(인증)·공통 정책(설정)"은 통합**, **"무슨 일을 하는가(업무·데이터)"는 시스템별 유지.** 이것이 실제 GMP 환경의 IAM(통합 계정·접근 관리) 모범과 일치하며, 그 자체가 CSV 교육의 좋은 사례가 된다(21 CFR Part 11 / EU Annex 11의 접근통제).

## 4. 아키텍처 선택

### 옵션 A — 통합 셸 + 공유 계층 (권장, 점진적)
- 6개 파일은 그대로 두고, 포털(index.html)을 **중앙 관리 콘솔**로 확장.
- 공유 데이터를 `gxpsuite:*` 네임스페이스에 두고, 각 시스템이 진입 시 이를 읽어 동작(현 SSO 패턴 확장).
- 장점: 기존 산출물(URS/FDS/구현계획서) 보존, 리스크 낮음, 빠름.
- 단점: 6개 파일에 동일 패치를 반복 적용해야 함(동기화 코드).

### 옵션 B — 단일 애플리케이션으로 병합
- 6개를 모듈로 합쳐 하나의 SPA로 재구성.
- 장점: 진짜 단일 시스템, 코드 중복 제거.
- 단점: 대규모 재작성, 변수·라우터 충돌 정리 필요, 교육용 "시스템별 산출물" 구조와 어긋남.

### ▶ 권장: **옵션 A로 진행** (교육 시연·Vercel 배포까지 충분). 장기적으로 운영 제품화가 필요하면 옵션 B + 공유 DB 검토.

## 5. 결정이 필요한 사항

### 5.1 ⭐ 역할(권한) 모델 — 가장 중요한 결정
한 계정이 6개 시스템에서 각각 어떤 권한을 갖는가? 시스템마다 역할 체계가 다르다(COA: 시험자/승인자/관리자, ELB: Manager/Operator, …).

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **(가) 슈퍼유저 단일** | 모든 계정이 전 시스템 전권 | 가장 단순, 시연 매끄러움 | 권한 분리 시연 불가 |
| **(나) Suite 역할 → 시스템 역할 매핑** | Suite 역할(관리자/QA/현장실무 등)을 시스템별 역할로 고정 매핑 | RBAC 시연 가능, 관리 단순 | 매핑표 설계 필요 |
| **(다) 사용자×시스템 역할 매트릭스** | 계정마다 시스템별 역할 개별 지정 | 가장 정밀 | 관리 UI 복잡 |

**권장**: 교육 시연 1차는 **(가) 슈퍼유저**로 빠르게, 이후 **(나) 매핑**으로 고도화.
(나) 매핑 예시:

| Suite 역할 | COA | LM | ELB | RIM | SEM | CVM |
|---|---|---|---|---|---|---|
| 관리자 | ADMIN | ADMIN | MANAGER | ADMIN | ADMIN | ADMIN |
| QA | APPROVER | QA | MANAGER | MANAGER | MANAGER | QA |
| 현장실무 | TESTER | TRAINER | OPERATOR | QC | QA | VAL |

### 5.2 통합 감사추적 — 포털에서 전 시스템 감사 이력을 합쳐 보여줄까? (권장: 예, 읽기전용 뷰)
### 5.3 환경설정 범위 — 공통(회사명·자동로그아웃)만 통합? 시스템 고유 설정도 포털로? (권장: 공통만 통합, 고유는 시스템 유지)

## 6. 단계별 구현 계획

### Phase 0 — 완료 (1차 SSO 통합)
- [x] 07. full 폴더, 포털 런처, 6종 SSO 복사본, super-user 자동 로그인

### Phase 1 — 중앙 계정관리 + 환경설정 (이번 작업 대상)
- [ ] 포털에 공유 계정 저장소 `gxpsuite:users` 신설 + 시드(관리자/실무자)
- [ ] 포털 로그인 → `gxpsuite:users` 인증 (admin/admin 하드코딩 제거)
- [ ] 포털 **계정관리** 화면: 생성·역할지정·활성/비활성·비밀번호 재설정
- [ ] 포털 **환경설정** 화면: 회사명·자동 로그아웃 (`gxpsuite:settings`)
- [ ] 각 시스템 `adoptSuiteSession()` 확장:
  - 포털 계정을 시스템 user 테이블에 upsert(동일 비밀번호) → 전자서명 정상 동작
  - 공통 설정(회사명·자동로그아웃) 전파
- [ ] 각 시스템에서 **계정관리·환경설정 메뉴 숨김**(통합으로 이전), 감사추적은 유지
- [ ] (선택) 5.1 역할 모델 (가)→(나) 적용

### Phase 2 — 통합 감사추적 + UX 정리
- [ ] 포털에 **통합 감사추적** 화면(6개 시스템 audit 집계, 읽기전용, 필터, CSV)
- [ ] COA 디자인 Starbucks 통일
- [ ] 포털 헤더/내비 일관화, 시스템 간 이동 동선 정리

### Phase 3 — 배포 (Vercel 정적)
- [ ] `07. full` 폴더를 Vercel 정적 사이트로 배포 (index.html 진입)
- [ ] 도메인·접속 안내, 데이터는 여전히 브라우저 localStorage(개인별)임을 명시
- [ ] (보완) 전 시스템 공통 **백업(JSON)/복원** 기능으로 데이터 이관 지원

### Phase 4 — 공유 DB 전환 (운영 지향, 교육 후)
- [ ] Supabase 도입: Auth(로그인 교체), Postgres(공유 데이터), RLS(계정·회사별 격리)
- [ ] 시스템별 `store.get/set`(동기, localStorage) → Supabase 쿼리(async) 리팩터링
- [ ] 1종 파일럿 후 6종 확대
- [ ] 서버 타임스탬프·불변 감사 테이블로 데이터 완전성 강화

## 7. 데이터·배포 로드맵

```
[지금] localStorage (개인 브라우저, 공유X)
   │  Phase 1~2: 통합 계정·설정·감사 (여전히 localStorage)
   ▼
[Phase 3] Vercel 정적 배포 — URL 생성, 데이터는 접속자 브라우저별
   │  + JSON 백업/복원으로 데이터 이관
   ▼
[Phase 4] Supabase (Auth + Postgres + RLS) — 다중 PC 영구 공유, 진짜 운영형
```
